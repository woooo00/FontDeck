## 单行被劈成两段 + 字体比对全库被门槛淘汰（2026-11-19 09:26，FD-20261119-092620）

用户报「少字或多字、字体不对」，备注「识别多字，字体识别没成功，特殊符号识别错误」。

### 一、一行文字被切成两段（`_bands_by_cores` 碎片 core）

渲染图 2988×164，图上**只有一行**文字，但 bands 是 `[[0,55],[55,164]]`：

```
行1 [0.521] ".........oooo."          ← 多出来的垃圾行
行2 [0.906] ": Initial state after startup: The screen defaults to 190'C ..."
```

y 投影（proj）从 y=32 起就 > 0，全程连续**没有空白**，所以第一级（严格墨迹段）
正确地只切出 1 段 —— 但单段会走 `_bands_by_cores` 兜底，而兜底用的是 15% 峰值阈值：

```
全局峰值 1189 → 阈值 178
y=41~43 的 proj 是 201~224，刚过阈值 → 单独成为一条 core [40,43]（高 4px）
y=60+ 是 x-height 主体 → 另一条 core
med = median([4, 60]) = 31 → min_gap = 15.5，而两段间距 17px > 15.5 → 不合并
分界落在 (43+60)/2 → 55，把一行从腰上劈开
```

**修法**：兜底里过滤掉 `frag_h` 以下的碎片 core（阈值与第一级一致，
`max(4, min(8, H*0.03))`）。过滤后只剩 1 条 core → 返回单段。

结果：`bands=[[0,164]]`，单行识别 **0.933**：

```
: Initial state after startup: The screen defaults to 190°C (temperature
```

**顺带修好了 `190'C`**：分段正确后 `°` 被读对（旧结果是 `190'C`）。
整行上下文完整，OCR 对特殊符号的判断也跟着变准。

### 二、字体比对返回空数组（slant 硬门槛把 729 个候选全杀了）

`font` 上下文里 `candidates: []`、`samples: []`、`durationMs: 8169` ——
跑了 8 秒，一个候选都没产出，面板显示「字体识别没成功」。

根因：精排阶段有一条斜体硬门槛

```python
if abs(stats["slant"] - cstats["slant"]) > 0.035: keep = False; break
```

而这一行的源端 `slant = 0.173`（注释里记录的正体是 -0.013~0、斜体是 0.062~0.090，
0.173 超出斜体上限一倍）。没有任何字体的 slant 能和 0.173 对上，
**729 个候选逐个被这条门槛淘汰，`refined` 为空 → 返回 `[]`**。

为什么 slant 会被拉偏：它是逐字符统计，71 个字符的长行里混进括号、破折号、
开头的 `·`，中位数就被带跑了。

**两层修法**：

1. **源端不可信时停用门槛**：先检查源 slant 是否落在已知区间
   （正体/斜体两段合并 = -0.05~0.12），不在区间内就判定「这个量测坏了」，
   本轮跳过 slant 门槛，其他判据照常。
2. **最终兜底不允许返回空**：`refined` 仍为空时，退回粗筛的老分（整行余弦，
   不含任何门槛）给 12 个候选并标 `fallback: true`。
   面板宁可显示「相似度低」，也不能显示「识别失败」—— 用户拿到 60 分的
   候选列表还能自己挑，拿到空列表什么也做不了。

## 行分段：全局阈值把短行整行吃掉（2026-11-18 17:47，FD-20261118-174711）

### 现象：四个症状其实是同一个根因

用户一次报了「少字 / 文字认错 / 字体不对 / 字号字距不对」。诊断日志里：

```
bands = [[0, 55], [55, 256]]
行1 [0.558] "....oo.oooo...."
行2 [0.858] "2mPature adjustment range: 15UCto 210C maximum operating temperature:"
字体最高 0.2276（Eras Medium ITC），并提示「推荐不可信」
```

但渲染图上明明是两行完整文字：

```
Temperature adjustment range: 150°C to 210°C; maximum operating temperature:
210±10°C.
```

### 根因：15% 峰值阈值是全局唯一的

`find_row_bands` 原本只有一套策略 —— 用 `proj.max() * 0.15` 找每行的核心带。
这隐含假设「所有行的墨量在同一量级」，这份稿直接推翻了它：

| 行 | y 范围 | 投影峰值 |
|---|---|---|
| 第一行（60+ 字符） | 32–135 | **1337** |
| 第二行（`210±10°C.`） | 144–223 | **133** |

阈值 `1337 × 0.15 = 200.5`，第二行峰值只有它的 10%，**整行一个像素都没进 strong**。
同时第一行内部被切成 `[41,45] [48,50] [60,112]` 三片碎片，`median` 被拉到 **4**、
`min_gap` 只剩 5，于是 9px 的间隔就过了关 → 分界落在 55。

连锁后果：
1. 上带（0–55）只剩字的顶部弧线 → OCR 读成 `....oo.oooo....`
2. 下带（55–256）是「第一行下半截 + 第二行」叠字 → `Temperature` 被横切读成
   `2mPature`，`150°C` 读成 `15UCto`，第二行**整行丢失**
3. 这两行垃圾文本被送进字体比对 → 余弦 0.2276 → 字体全错
4. 行框高度错成 201（真实 105）→ 字号 / 字距跟着错

### 修法：两级分段，墨迹段优先、核心带兜底

```
第一级  严格连续墨迹段（proj > 0）
        · 行与行之间哪怕行距再紧也总有一段近乎全白的间隔
        · 一行内部从大写上伸 → x-height → 下伸，投影始终 > 0
        · 所以连续段天然就是行，且不受各行墨量差异影响
        · 1~2px 抗锯齿断裂并回去；< frag_h 的碎片段并到邻段
第二级  只在「第一级只切出一段」时启用 = 原核心带算法
        · 那代表行距紧到墨迹真的粘连（超粗字 / 紧行距）
        · 历史稿走的正是这条路径，行为保持原样
```

碎片阈值 `frag_h = max(4, min(8, H*0.03))`：正常 4x 渲染下 0.5pt = 2px，
真实文字连上伸下伸也不低于 8px。误差方向是安全的 —— 误判只会把两段并成
一条更宽的带，不会把一行劈开。

### 实测

渲染图 3528×256，同一份 png：

| | bands | 行文本 | 字体最高分 |
|---|---|---|---|
| 旧 | `[0-55, 55-256]` | `....oo.oooo....` / `2mPature ... 15UCto 210C` | 0.2276 |
| 新 | `[0-139, 139-256]` | `Temperature adjustment range: 150°C to 210°C; maximum operating temperature:` 0.938<br>`210±10℃.` 0.813 | **0.9067** |

字体第一名变成 **HarmonyOS Sans Light**（base 0.9318、字重吻合 0.972、字宽比 1.026），

## 板块间隙回归 + 恢复页间距重排（2026-11-18 17:10，`style.css?v=54` `app.js?v=50`）

### 一、间隙要留，但里面不能透内容

上一版把顶栏和页签之间的缝合掉了（0px），用户明确否掉：**那个间隙是用来
区分板块的，必须留着**，只是不能让滚动内容从里面透出来。

于是改成：留 8px（`--sticky-gap`），并且给间隙垫一层实底。

```css
.topbar::after,
.tabs::after {
  position: absolute;
  top: calc(100% - var(--r-lg));
  height: calc(var(--r-lg) + var(--sticky-gap) + 1px);
  background: var(--bg);   /* 实色，不是玻璃 */
  z-index: -1;             /* 待在自身背景之下，圆角才是圆的 */
}
```

三个细节，缺一个都会漏：

1. **向上多盖一个圆角半径**：`border-radius` 是裁剪，被裁掉的三角同样露卡片，
   只盖「下方 8px」是不够的。
2. **`z-index: -1`**：垫层压在自身背景之下，圆角保持圆的；如果放上面，角会被
   切成直角。
3. **`+1px`**：`top: 100%` 的百分比基于 padding box，不含底部 1px 边框，
   不补的话垫层末端正好差一条，滚动时露一行字（实测覆盖到 94.5，间隙却到 95.5）。

顺带删掉了上一版的 `body.is-scrolling`（滚动时圆角收成直角）—— 垫层已经解决
漏内容，圆角可以常驻，不会随滚动闪。**JS 里那段 scroll 监听也一并删除。**

`filters` 单独一条：它下方没有间隙（紧接常用区），所以 `::after` 只填自己的
圆角缺口（高 12px+1），不往下延伸，否则会盖住下面内容的顶部。

### 二、吸顶偏移只允许在一个地方定义

`.filters` 的 `top` 又在窄屏 `@media` 里重复了一遍（老坑复发，滚动后 filters
压在页签上 8px）。彻底抽成变量：

```css
:root {
  --sticky-tabs-top: calc(var(--topbar-h, 88px) + var(--sticky-gap, 8px));
  --sticky-filters-top: calc(var(--sticky-tabs-top) + var(--tabs-h, 37px) + var(--sticky-gap, 8px));
}
```

媒体查询里**只改 padding，不再碰 top**。实测（未滚动 / 滚动 700 后一致）：
`topbar.bottom=87.5 → tabs.top=95.5`（缝 8.0）、`tabs.bottom=132.5 → filters.top=140.5`
（缝 8.0），三块全部正常吸顶。

### 三、恢复页纵向节奏重排

上一版把 `#recStatus` / `.rec-result` / `.rec-sep` 的空态都隐藏了，间距的基础
（`<p>` 默认 1em 外边距 + 空的 status/result 撑高）跟着一起消失，整页挤成一团。

而且 `.rec-intro` / `.rec-hint` 本来**没有任何样式规则**，全靠 `<p>` 的默认
margin —— 这就是"间隔乱来"的根源。

现在每一段都是显式数值（4/8 的倍数）：

|---|---|

| 主按钮 → 分区块 | 22 |
| 分隔线 → 「排版整理」 | 16 |
| 「排版整理」→ 按钮行 | 12 |

同时把 `<div class="rec-sep">` 删除，改成 `.rec-sect` 包住「排版整理 + 两个按钮

## 吸顶块的缝 / 恢复页空气泡 / tabs 圆角（2026-11-18 16:35，`style.css?v=49` `app.js?v=49`）

用户一次提了四个视觉问题，其中第一个是**真 bug**，而且是两个原因叠加。

### 一、滚动时顶栏底下漏内容 —— 不是圆角，是 4.5px 的缝

实测：

```
topbar: h=87.5  bottom=87.5
tabs  : top=92   ← 写死的
filters: top=131 ← 也是写死的
```

顶栏实际高 **87.5px**，而 tabs 的 `top` 写的是 92px —— 中间一条 **4.5px 的缝**，
滚动时卡片正好从缝里整条穿过去（截图里"Microsoft JhengHei"能认出来）。
filters 的 131 比真实值多 6.5px，同理。

为什么会有小数：顶栏高度由 brand 行 + 搜索行的行高算出，不是整数。
写死整数必然对不上，而且窄屏 media query 里还有一条 `.filters { top: 127px }`
独立写死，宽屏改了窄屏不动。

修法：不再写死，运行时实测回写 CSS 变量。

```js
function syncStickyTops() {
  var h1 = tb.getBoundingClientRect().height;   // 87.5，不能用 offsetHeight（取整成 88）
  var h2 = tabBox.getBoundingClientRect().height;
  root.setProperty("--topbar-h", h1 + "px");
  root.setProperty("--tabs-h", h2 + "px");
}
```

配合 ResizeObserver + `document.fonts.ready + resize` 重测（字体加载前后 tab 行高
实测从 39.5 变 37）。结果：`tabs.top = 87.5 = topbar.bottom`、`filters.top = 124.5
= tabs.bottom`，两条缝归零。

**圆角真的会露内容**（这是另一半）：`border-radius` 是裁剪，被裁掉的三角会露出
下面滚过去的卡片，物理上无解 —— 遮住缺口就等于取消圆角。所以加 `body.is-scrolling`，
滚动期间把三个吸顶块的下圆角收成 0，停 180ms 再还回来（0.16s 过渡）。
真实浏览器实测 `SEE=YES | 圆角 min=0.0 max=12.0`，收放都对。

同时把三个吸顶块的背景提实：topbar 0.72→0.9、tabs 0.66→0.88、filters 0.6→0.88。
半透明吸顶块滚动时整条都在透内容，不只是缺口处。

| `.rec-result` | `margin-top:16` 的外边距 | `:empty { display:none }` |

recLayoutStatus h=0 / sep显示=none`。

### 三、恢复页 tabs 下圆角

`body[data-pane="recover"] .tabs` —— 恢复页下方没有筛选条，tabs 就是这一块的收口。
字体库页不加（它紧贴 filters，两个圆角叠着会形成平行弧线）。`switchPane` 里

### 验证方法的坑（第二次踩）

1. **`offsetHeight` 会取整**：87.5 变 88，留下 0.5px 缝 = 2x 屏上一整条物理像素。
   要精确值必须用 `getBoundingClientRect().height`。
2. **`@media` 里的同名规则会盖掉主规则**：`.filters { top: 127px }` 在窄屏媒体查询里
   躺了很久，改主规则完全无效，还以为是变量没生效。
3. **headless 的 `--virtual-time-budget` 不推进 CSS transition**：`border-radius`
   从 0 过渡到 12px，读出来永远是起始值 0px，看起来像"规则没生效"。
   真实浏览器一读就是 12px。**涉及 transition 的计算值，一律用内置浏览器验。**
4. 探针里读 `style.borderRadius` 对含 `var()` 的简写会返回空串，导致"0 条规则"的假结论。

## 托盘只跟最后一张常用卡展开（2026-11-18 16:15，`app.js?v=45`）

上一版给 `.fav-grid` 补 padding-bottom 撑托盘，条件是「在常用区 + 向下展开」。
用户把常用区展开成多张后发现：**展开中间任意一张，托盘也会跟着拉长**，
这不对——中间的卡展开后下半截本来就压着下面那张卡，托盘底下不会露空档。

改成三段判定 `top >= 0 && isLastFavCard(card)`：

```js
function isLastFavCard(card) {
  var g = document.getElementById("favGrid");
  if (!g || !g.contains(card)) return false;
  var kids = g.querySelectorAll(".card");
  var last = null;
  for (var i = 0; i < kids.length; i++) {
    if (kids[i].offsetParent) last = kids[i];   // .is-extra 是 display:none
  }
  return last === card;
}
```

折叠时多出来的卡挂在 `.is-extra`（`display:none`）上，`offsetParent` 为 null，
据此得出「当前可见的最后一张」。另外 rAF 里改成**两个分支都写**
`setFavRoom(...)`，不满足条件时显式清 0，否则从「末卡」切到「中间卡」时
上一张留下的 padding 会残留。

实测（4 张常用卡全部展开，探针读 DOM）：

| 状态 | paddingBottom | 托盘高度 | 末卡底 / 托盘底 |
|---|---|---|---|
| 初始 | `""` | 275 | 488 / 499 |
| 中间卡（第 2 张）展开 | `""` | **275（不变）** | 488 / 499 |
| 末卡展开 | `"80px"` | **344** | 556 / 568 |

### 验证方法上的一个坑

headless + `--virtual-time-budget` 下 `requestAnimationFrame` **不可靠**：
同一个探针跑两次，一次中间卡展开成功、一次连 `is-big` 都没加上，
结论完全相反。改用内置浏览器（browser_id=1）打开探针页、真实等待后
用 `dom_cua_get_visible_dom` + 小区域截图读日志，两次结果才稳定。
**凡是依赖 rAF 的状态验证，别信 virtual-time 截图。**

边框 + 顶部内高光，两条 0.9/0.85 的白线紧挨着叠成一根亮杠。
**只删其中一条的话，白线还在**，很容易误判成「没改对」。

两条都去掉，层次改由底色差（筛选条 0.6 白 / 常用区淡紫）承担。
底部那条 `inset 0 -1px` 保留 —— 它在托盘下沿，是托盘的立体感来源，不碍事。

### 二、托盘不跟卡片走，是因为卡片绝对定位

`.card` 是 `position: absolute` 放在固定高度 58px 的 `.slot` 里，展开时
**只改自己的 height**，占位格纹丝不动 —— 这是当初为了「相邻行不重排」
刻意做的（`app.js` 顶部注释有写）。代价就是：卡片长出 68px 之后，
托盘背景还停在原位，预览等于「悬」在板块外面。

修法：`expandCard` 里判断卡片在不在 `#fav` 内、且是向下展开，给
`.fav-grid` 补一段等高的 `padding-bottom`，托盘自然被撑高；收起时清空。
`.fav-grid` 加了 `padding-bottom` 过渡，和卡片 height 动画同为 0.2s，
否则容器先跳、卡片后长，看着像两件事。

**只对常用区做**：列表区几百张卡，撑高会导致滚动位置跳动，而且列表里
本来就没有「底板」这个概念，卡片直接盖在背景上是对的。

向上展开（`top < 0`）不补 —— 那要补的是顶部空间，而常用区只有一张卡、
位置靠上，不会触发。

## 吸顶失效（真 bug）+ 常用区收到 1 个（2026-11-18 15:52，`?v=44`）

### 一、顶栏 / tab / 筛选条根本没吸顶

用户要求「滚动时这块不动」，一查发现它**一直是坏的**，只是没人报。

根因在 `html, body { overflow-x: hidden }`：
按 CSS 规范，一个方向设成 `hidden` 会把另一个方向的计算值从 `visible`
变成 `auto` —— 于是 **body 变成了滚动容器**，而真正的滚动发生在 `html` 上。
`position: sticky` 的参考系是最近的滚动祖先（body，它自己不动），
所以三个 sticky 块全都跟着页面滚走了。

**实测**（`data/_analysis/probe-sticky.html`，滚 500px 后读
`getBoundingClientRect().top`）：

| | topbar | tabs | filters |
|---|---|---|---|
| `overflow-x: hidden` | **-500** | -408 | -373 |
| `overflow-x: clip` | **0** | 92 | 127 |

**修法**：`overflow-x: clip`。`clip` 只裁剪、不创建滚动容器，
所以横向溢出照样裁掉（抽屉 `translateX(100%)` 那个问题仍然解决），
sticky 又能相对视口工作。Chromium 90+ 支持，CEP 99 够用。
保留一行 `overflow-x: hidden` 作老引擎兜底（那种引擎上 sticky 本来就是坏的）。

横向裁剪这个原始需求不能丢：抽屉默认藏在右边界外，不裁的话
顶栏右侧按钮会被推出视口。

### 二、常用区只常显 1 个

`app.js` 的 `FAV_SHOW` 3 → 1。「其余 N 个」按钮和展开逻辑都是按这个变量
算的，改一处即可（现在显示「其余 3 个」）。

常用区在下滑之前不该占掉半屏 —— 原来 3 张卡 + 标题就吃掉 200px。

### 已知副作用（吸顶修好后才会显现）

筛选条底部圆角处，滚动经过的卡片会从左右两个 12px 的圆弧缺口露出一点。
因为那层有 `backdrop-filter: blur(18px)`，透出来是柔和的色块而不是硬切口，
实测看着可以接受。如果觉得碍眼，可以给 `.filters` 提高背景不透明度
或者去掉它的下圆角。

## 字体匹配：整行 → 切片级（2026-11-18，FD-20261118-145147）

用户报「候选字体 100% 是错的，下面 98% 的才对」。
一行 URL `https://www.ukliss.co/`，旧结果 JhengHei Bold 0.888 压住
真身 HarmonyOS Sans Medium 0.8676（用户确认 98% 那个才是对的）。

### 根因一：整行比对在长文本上分辨率不够

`compare_line_fonts` 把整行归一化到 **1024 列 × 96 行**的网格。
19 个字符摊到 64 个网格列里，**每个字母只有 3 个格子** ——
「这个 a 的碗是圆是方」「s 的收笔往哪弯」全被平均掉了，
剩下的主要是「整体墨迹分布」，而几何黑体在这一层几乎一样。
于是前四名挤在 0.868~0.888（差 2%）的窄带里，排序基本由笔画粗细决定。

**修法**：改用 OCR 的「粘连切片」当样本。OCR 常把 2~3 个字母并成一格
（`ht` / `tp` / `uk` / `lis` / `co`），框里本来就是多个字母，
所以**整串一起渲染**再比（拿 `ht` 去比单字 `h` 必然全错 ——
这正是旧代码只敢用 `length===1` 的切片、最后退化到只剩 `w` 和 `1`
两个样本的原因）。2~3 个字母铺满 64 列，每个字母 5~7 个格子，
分辨率高一个量级。

实测同一组数据：

| 样本 | 真身 | JhengHei Bold | 逐片一致性 |
|---|---|---|---|
| 整行（旧） | 0.888 | **0.888**（错排第一） | — |
| 切片（新） | **0.989** | 0.966 | 真身五片 0.987~0.992（极差 0.005）；JhengHei 0.933~0.980（极差 0.047） |

合并权重：切片 0.8 / 整行 0.2。整行不是没用，它带字距、词距、
整行宽高比，这些切片丢了。

### 根因二：字重测量被渲染尺寸带偏

`stroke_weight` 会把墨迹缩放到 `NORM_H=96` 再数面积，所以候选字体
渲染在 64px 时**要先放大**到 96 —— 插值 + 阈值化让笔画系统性变细。
原稿是 236px（缩小 0.4），两边缩放方向相反。

实测原稿 `stroke_weight = 228.9`：

| 渲染尺寸 | HarmonyOS Medium | JhengHei Bold |
|---|---|---|
| 64px（旧） | 211.4 → wfit 0.923 | 228.2 → wfit **0.997** |
| 96px（新） | 229.5 → wfit 0.998 | 222.5 → wfit 0.972 |

旧配置下真身被判成「比原稿细 7.6%」，而 Bold 恰好落在 228，
于是 `score = base × (0.5 + 0.5×geo)` 里那 50% 的几何修正
把形状证据已经判对的排序整个翻过来。改成 96px（1:1，几乎不缩放）后真身命中。

### 结果

| | 旧 | 新 |
|---|---|---|
| Top1 | Microsoft JhengHei Bold 0.888 | **HarmonyOS Sans Medium 0.9579** |
| Top3 | HarmonyOS Medium 0.8676 | JhengHei Bold 0.9340 |
| 耗时（729 候选） | 2052ms | 2.7~3.3s |

### 切片的过滤规则（每条都有代价）

1. **含标点一律丢** —— 句点在所有字体里就是个小圆，不携带特征；
   `W.` / `S.` / `$:I.` 这类还多是切分噪声。
2. **宽/高 < 0.32 的极窄字丢** —— `l`、`i`、`1` 在几百款字体里长一个样。
3. **必须在行文本里找得到** —— OCR 会给幻觉字符，对不上直接丢。
4. **置信度门槛只设 0.25，不作主判据**。汉字单字没有上下文，
   OCR 置信度天然只有 0.3~0.5（实测「滚滚长江东逝水」全部 0.29~0.50）。
   一开始按英文的 0.6 去卡，中文切片被全部误杀，只剩整行比对。
   真正把关的是第 3 条；文本认错的切片会在 Python 侧因为余弦掉到
   0.5 以下被剔除，不会污染排序。

**同一个字出现两次只留一个**（「滚滚长江」）—— 重复切片等于给这个字投两票。

### 回归验证

| 案例 | 类型 | 旧 Top1 | 新 Top1 |
|---|---|---|---|
| FD-20261118-102207 | 中文，华文琥珀 | STHupo 0.9661 | STHupo 0.9671 ✓ |
| FD-20261118-145147 | 英文 URL | JhengHei Bold | HarmonyOS Medium ✓ |
| FD-20261111-114755 | 英文说明书 | Aptos 0.8574 | HarmonyOS Medium 0.8555（Aptos 掉出前五）|

### 附带改动

- `render_line` 渲染尺寸 64 → 96（见根因二），同时加了 `_pil_font`
  对象缓存：原来每次渲染都 `ImageFont.truetype` 重新读整个字体文件
  （中文字体 10~30MB，单次 8~10ms），切片比对要把渲染次数放大 5 倍，
  不缓存会到 10 秒以上。
- 诊断日志新增 `sliceFit`（形状吻合度），以后「字体不对」能一眼看出
  是形状判错、还是被字重/字宽修正翻盘。

### 没解决的部分

**相对百分比的显示仍然会让用户误判。** 0.9579 显示成 100%、
0.9340 显示成 97.5% —— 用户在两个都接近 100% 的情况下依然没有依据
判断该信哪个。这是展示层问题（相对归一化 vs 绝对相似度），
本次只修了排序，没动 UI。

## 阶段 2-③ 背景回归柔和、分类精简（2026-11-18 14:43，`style.css?v=40`）

两条反馈：**底部彩色背景太突兀**、**分类只留第一组**。

### 一、背景：只换形态，不还明度差

上一版为了让「静止时磨砂也成立」，把背景改成 118° 的**硬边斜向色带**
（每段过渡只有 0.8%），被 blur 后确实能看出「糊开了」，但相机视角看就是几道条纹，
太抢眼 —— 在一个看字体的工具里，背景本来就不该有存在感。

改回四团柔和的径向光斑 + 162° 淡渐变。**但基色没有一起回到 `#eceeff`**：
一旦和卡片同亮，玻璃立刻退回「白框」（这是 2-① 踩过的坑）。现在基色 `#e3e7fd` 左右，

结论：**玻璃的「透光」和「模糊」是两件事**。透光靠明度差 + 半透明，跟背景是否有
锐利边缘无关；模糊才是靠高频细节。砍掉色带等于只砍了模糊的可见度，透光不受影响。

在 380px 面板里挤压明显，按用户要求整组删除（含 `.filter-divider` 死规则）。

**JS 不用改**：`app.js` 的 chip 逻辑是 `querySelectorAll(".chip")` 通用遍历，
没有对 `data-key="scope|health|dup"` 的单独引用；`state.scope/health/dup` 恒为空，

不属于筛选入口，保留。

`.filter-group` 的 `flex: 0 0 100%` 保留 —— 7 个胶囊在 380px 下装不下，
「手写」仍然换到第二排（与设计稿一致），只是不再有第三、四排。

## 阶段 2-② 玻璃材质返工 + 常用区展开层级修复（2026-11-18 下午）

用户反馈两条：**常用区最后一张卡展开时被下面列表卡压住**、**卡片还是白底框没实现磨砂**。
两条都不是「微调参数」能解决的，各自有具体原因。版本 `style.css?v=39`。

### 一、展开卡被压住：两个叠在一起的原因

**原因 1：`.fav` 加了 `backdrop-filter` 就变成了堆叠上下文。**
`backdrop-filter` / `transform` / `filter` / `opacity<1` 都会创建堆叠上下文。
`.card.is-big` 的 `z-index: 18` 只在这个上下文**内部**比较，整个 `.fav` 的绘制顺序
又早于后面的主列表 → 展开的常用卡直接被列表卡盖住。修法：`.fav` 去掉 backdrop-filter，
要模糊由里面的卡片自己负责。

**原因 2：去掉之后还不够 —— 两层 z-index 撞在同一个数值上。**
常用区和主列表是独立容器，展开卡都是 18，浏览器退回**按 DOM 顺序**决胜，
主列表在后 → 还是它赢。修法：`#favGrid .card.is-big { z-index: 18 }`、
`#grid .card.is-big { z-index: 17 }`，错开一档，两级都仍然低于吸顶栏（19/20）。

两个原因必须**都**修，只改第一个的话现象几乎不变，很容易误判成「没改对」。

### 二、磨砂玻璃：磨砂感 = 背后有东西被糊掉

第一版失败在三处，缺一处就不成立：

| 问题 | 第一版 | 现在 |
|---|---|---|
| 背后没东西可模糊 | 平滑灰底，模糊前后一模一样 | 背景改成**边界略硬的斜向色带**（118°，0.8% 过渡），被 blur 掉后能看出「糊开了」 |
| 没明度差 | 背景 `#eceeff` 和卡片几乎同亮，半透明白叠上去没有任何对比 | 基色压到 `#dfe4ff`（暗一档），玻璃才浮得起来 |
| 砍掉了真模糊 | 为了滚动性能只在悬停时开，静止时靠半透明硬撑 | 卡片本身 `blur(16px) saturate(160%)`，回到真磨砂 |

另外 `--sheen` 的白色从 0.34 压到 0.24、卡片白度 0.56→0.40，否则白光把透色盖死。
`saturate` 给到 200% 会变成「彩色塑料」，160% 才像玻璃。

**诚实说明**：静止时「模糊」这条特征**肉眼不明显**，因为背景是平滑色带、没有字形这种
高频细节。最能看出磨砂的时刻是**悬停展开盖住相邻卡片**时 —— 下面那张卡的字被糊开、
只剩柔和色块。这是场景的物理限制（一个看字体的工具，背景不能放干扰内容），
不是没做。

`.fav` 底色同时从 0.5 压到 0.28：原来是「在背景上又铺一层白」，导致常用区的卡

## 阶段 2-① 玻璃材质 + 悬浮（2026-11-18）

纯视觉改版第一步：全站卡片换成半透明磨砂玻璃，加悬浮感。版本 `style.css?v=33`。

### 三个必须写下来的判断

**1. 磨砂玻璃必须先有「可被模糊的东西」。**
原来背景是纯色 `#f6f6f7`，玻璃卡在上面只会显示成「白一点的方块」。
所以 `body::before` 加了一层 `position: fixed` 的彩色光斑（四团 radial-gradient，
透明度 0.11~0.26，紫/蓝/粉/青）。固定而不是随滚动，是为了让卡片滑过时光斑
相对移动 —— 透出的色温会变，「活」的玻璃感就来自这一点。

**2. 列表卡**不开**真 `backdrop-filter`。**
`backdrop-filter` 每个元素都要单独合成一层，字体列表是无限滚动的（PAGE=48，
能累积到几百张）。几十上百层同时模糊，在 CEP 的 Chromium 99 里滚动必然掉帧。
所以改成「伪玻璃」四件套：
半透明白（`--glass-2` 0.56）+ 斜向光泽（`--sheen`）+ 上沿 1px 高光（`--inset-hi`）
+ 负 spread 分层阴影（`--lift-1/2/3`，阴影只往外扩、不会在卡内发灰）。
卡片背后只有极淡的光斑、没有锐利内容，模糊与否肉眼分辨不出。

真模糊只给**数量可控**的元素：topbar / tabs / filters / 常用区 / 抽屉 / toast，
以及**悬停展开的那一张**（同一时刻只有 1 个，开销可忽略）。

**3. 看字形的地方不能透光。**
`.detail-preview`（字体详情大样张）、`.sim-glyph`（相似字体缩略图）、各种输入框
（`#search` / `.rec-line-input` / `.rec-paste-input`）用 `--glass-4`（0.93）或 0.82~0.86：
彩色光斑透上来会给笔画边缘染色、看着变粗，判断字体会失准。
玻璃质感靠亮边 + 内高光保留，只把「透光」这一项拿掉。

### 变量体系（改之前先看这段）

| 变量 | 用法 |
|---|---|
| `--glass-1..4` | 四级白，1 最透（大面积容器）、4 近实底（看字形、输入框） |

| `--lift-1/2/3` | 三级悬浮阴影（负 spread） |
| `--blur-s/m/l` | 三档模糊，留给数量可控的元素 |

## 行内分段：一行里多套样式分开识别与还原（2026-11-17）

用户要：同一句文本里字体/字号不同时，要分开识别、分开还原。

### 为什么不做「自动检测行内样式」

三条路都实测过，区分度不足，硬切必然误伤：

| 信号 | 单一样式稿的噪声 | 真实混合稿的信号 | 结论 |
|---|---|---|---|
| 字框高度（局部最大） | 最高 **22.6%** 跳变 | 1.5× 字号才 20~30% | 与噪声重叠 |
| 上下缘包络（分段中位数差） | 0.17~0.24×行高 | 基线变化 0.33 | 只能测基线 |
| 笔画宽度（平台比值） | 最高 **1.60** | Regular→Bold 1.67 | 与噪声重叠 |

根因是信息量：这批稿最小字号只有 3.7pt，笔画宽 **2px**，字重差异就是
±1px，与栅格化噪声同量级；整行渲染比对又会因字距漂移整体对不齐
（实测单一样式稿也出现大片"低分区"，其实是对齐失败）。

### 改成「按墨迹空隙拆分」（可控，100% 不切断笔画）

- `packages/ocr/worker.py` 新增 `split_line_gaps()`：给定行框和段数 n，
  在接近等分处找**真实空白列**下刀。切点选择用「**宽度主导 + 距离为辅**」——
  只按距离会切进单词（字母间也是全零列，实测把 `Welltop` 切成 `Wellt|op`），
  只按宽度会切到离目标很远的大空档。
- `packages/ocr/src/client.ts` 加 `splitLine()`；`cmd: "splitline"`。
- 新接口 `/api/recover/split-line`（png + box + n → 段框）与
  `/api/recover/ocr-lines`（png + boxes → 每段文本，直接走整行识别器）。
- 面板 v28 / CSS v17：单行识别结果下出现「2 段 / 3 段」按钮。拆开后每段
  一行：文本可改、字体可单独选、可点「取消分段」回到整行。
- 恢复：每段一个 item（自带 doc 和字体），复用 `fdRecoverApply`，**JSX 没改**。
- 诊断日志新增「行内分段：N 段 / 段i 文本 字体 置信度」。

| 场景 | 结果 |
|---|---|
| 混合稿（Regular 56px + Bold 96px 拼接） | 段1 `Weight:` → Arial **Regular** 0.9465；段2 `BOLD MIXED` → Arial **Bold** 0.9778 |

| 同稿拆 3 段 | `Manufacturer:` / `Guangzhou Welltop` / `Intelligent Appliance Co., Ltd`，全是完整词 |

## OCR 错字污染字体比对：三个症状同一个根因（2026-11-11 12:10）

日志 `FD-20261111-114755`：用户同时报「字体不对 / 字号或字距不对 / 恢复后位置不对」。
一行 3.7pt 的英文 `Manufacturer: Guangzhou Welltop Intelligent Appliance Co., Ltd`，
推荐 Aptos Regular，识别置信度只有 **0.837**。

### 结论：三个症状同源

OCR 读错了三处（`Welltop→Weltop`、`Intelligent→Intlligent`、`Co., Ltd→Co, Ltd`）。
整行字体比对是**拿识别出的这句话去渲染每个候选字体**的，错字一改，
整行宽度和字形全变，排名跟着歪；字号又靠整行宽度闭环，字体一错，
字号/位置在视觉上就跟着偏。实测：

| 比对用的文本 | Top1 | Aptos 名次 |
|---|---|---|
| OCR 结果（含 3 处错字） | Aptos Regular 0.8574 | 1 |
| 用户原文（正确） | DM Sans 9pt Regular 0.9022 | 掉出前 8 |

而字号 / 位置 / 坐标换算**本身是对的**：墨迹高 3.31pt、字号 3.71pt，
`字号/墨迹高 = 1.12`（西文正常 0.9~1.3）；`originY = topY - ph` 是选区左下角，
`boxToDocPoint` 用 `originY + (pngH-box.b)/scale` 算墨迹底边，坐标系自洽。
所以不要去改 `fdRecoverApply` —— 改了会把正确的换算弄坏。

### 本轮改动

- **面板主动提示**（`app.js` v26 / `style.css` v15）：任一整行置信度 < 90% 时，
  显示醒目警示条「错字会把字体、字号、位置一起带偏，把原文粘到下面会自动重算」，
  置信度标签变色、粘贴框高亮。回填本来就调 `doMatchFont()` 重跑比对，

- **诊断日志加两条自检**（`apps/service/src/main.ts`）：
  `--- 字体 ---` 段新增「比对文本」，能分清推荐基于 OCR 还是用户原文；
  `--- 恢复 ---` 段新增「字号自检：墨迹高 X pt，字号/墨迹高 Y（正常 0.9~1.3）」，
  一眼分清是几何换算错还是字体选错连带。
- **修回归退化**：`stroke_weight` 曾被改成 `area×NORM_H/h²` 的 O(1) 近似，
  但插值 + 阈值化让缩放后的面积非线性变化，而原稿（4 倍几何）与候选
  （PIL 64px）缩放方向相反，字重误差被系统性带偏，三行英文稿的
  HarmonyOS Sans 被 Myriad Pro 顶掉。已恢复 resize 版；性能靠漏斗解决，

- 回归脚本补齐字体断言（此前 121909 / 144316 / 145847 三例只验了行数和文本，
  漏掉过「MiSans → PT Sans Italic」的退化），并把斜体改成硬门槛：
  逐字符斜度 `slant`（正体 -0.013~0、斜体 0.062~0.090，阈值 0.035），
  因为整行重心拟合测不出逐字符倾斜。

- **3~4pt 的小字无法精确鉴定字体**：字形信息量不够。叠加图、整行比对、

## 字体比对重做：细体窄身稿推成粗斜体（2026-11-11）

用户报「字体不对」，日志 `FD-20261111-091907`：细体、窄身、正体的英文说明文字，推荐结果却是 **Franklin Gothic Heavy Italic**（粗斜体）。

### 根因（三层）

1. **渲染分辨率太低**：几何按 1pt = 1px 回传，一行 12pt 的说明文字只有 **12 像素高**，字形糊成黑块。OCR 因此出现 `outiook`（应为 outlook）、`reaa?` 这类幻觉，字体比对更是只能比「墨迹密度」。
2. **特征把字宽字重抹平**：`line_feature` 把整行**同时**拉到 1024×96（宽高各自拉伸）→ 候选字体的窄/宽被抹掉；再用**余弦**比密度向量 → 余弦对整体缩放不敏感 → 粗/细几乎不体现。结果所有候选挤在 0.84 附近，Top1 与 Top2 只差 **0.4%**，等于随机。
3. **粗筛漏掉正确答案**：只用「老分前 24」进精排，而正确答案（Arial，字宽比与原稿几乎一致）老分只有 0.8833，被直接滤掉 —— 用户在前六名里根本看不到它。

### 改了什么

| 改动 | 效果 |
|---|---|
| 几何渲染按面积自适应放大（≤20 万像素 → 4 倍，≤50 万 → 2 倍，更大 → 1 倍） | OCR 幻觉消失：`outiook`→`outlook`、`reaa?`→`?`；坐标同步放大，`scan.scale` 同步放大，文档坐标换算不用改 |
| 渲染改为**按轮廓包围盒局部绘制** | 4 倍分辨率下不再为每条轮廓分配整幅画布（18 行俄语稿原本要累计分配几十 GB）；**顺带把俄语长文识别从 46s 降到 4.6s** |
| 候选排序加**字宽 / 字重 / 倾斜一致性**核对 | 把「像不像」拆成三个可核对的量；**只做 15% 修正，形状证据（余弦）仍是主项** |
| 粗筛改三路并集：老分前 40 ∪ 字宽最近 60 ∪ 密度最近 60 | 正确答案不再被提前滤掉 |
| 推荐候选 6 → **12** 个 | 真身常排第 7~10 位，只给 6 个用户看不到 |
| 面板新增**「手动指定字体」搜索框** | 推荐只是「最相似」不是鉴定；输名字直接从本机 781 个 face 里挑（存显示名，AI 侧 `getByName` 能命中） |
| 诊断日志增加**行级几何**（字宽比 / 密度 / 倾角） | 下次报「字体不对」，一眼看出是字族、字重还是斜体的问题 |

### 踩过的坑（都留档了）

- **字宽特征一开始是错的**：切出来的「字符块」是列区间，高度仍是整行高，直接拿来算宽高比等于「块宽/行高」，精度全废（每块高度都等于行高）。必须再取一次**紧致 bbox**。
- **一致性权重不能高**：乘积会让「衬线斜体」这种形状明显不对、字宽却接近的候选顶掉正确答案；50% 权重会让 Sans Serif Collection 顶掉 HarmonyOS Sans。**叠图核对**（`scripts/compare-glyphs.py`）两次都证明老答案是对的，所以最终定成 15%。
- **整行 IoU 不可行**：字距差异会沿行累积错位，分数全掉到 0.2 且没有区分度；字符级 DP 对齐能救，但目前不作为主分。

### 结论（写给用户也写给自己）

这份稿子的**真身是 Arial**（叠图里红黑几乎完全重合）。字体识别本质是「最相似推荐」，不是鉴定；推荐永远可能偏，但**手动指定入口保证能选到正确的那个**。

`0xc0000005` 是原生内存访问违例。**JS 的 try/catch 完全挡不住，也不会留 JS 堆栈**，所以「加容错」没用，只能把可疑的宿主调用全部换掉。

### 为什么上一轮的"修复"会崩

上一版 `fdSplitTextLines` 读 `Line.visibleBounds` 必抛错，被内层 catch 吞掉 —— 也就是说**属性复制、建文本框、translate 这些代码从来没在真实 AI 里执行过**。修好第一行之后，整条路径第一次真正跑起来，里面全是没验证过的宿主调用：

| 调用 | 判断 |
|---|---|
| `a2[keys[k]] = a1[keys[k]]`（CharacterAttributes 上用**动态属性名**赋值） | 首要嫌疑，ExtendScript 宿主对象的属性分派最容易被这样打穿 |
| `merged.note = ...` / `src.note`（PageItem 宿主属性读写） | 未验证 |
| `src.textRange.paragraphAttributes`、`src.lines[q].contents` | 未验证 |
| `a1.fillColor` / `horizontalScale` 读出来直接赋给新框（可能取到无效值） | 未验证 |

### 处理

**保守重写**，只保留在真实 AI 里反复验证过的调用：`textFrames.add` / `kind` / `contents` / `characterAttributes.size` / `textFont = app.textFonts.getByName(...)` / `visibleBounds` / `translate` / `hidden`。字体改成「读字体名 → 按名字重新查」，不跨文本框传递宿主对象引用；颜色、字距、水平缩放**这轮不复制**（稳定优先）。区域文字自动折行的 `lines` fallback 也暂撤。

**精确位置改用纯 JS 全局变量** `fdMergeRowPositions` + `fdMergeFrameRef`，不碰 `note`；只有「当前对象正是上次合并产物且行数一致」才用，用完即清空 —— 顺带修掉「另一个恰好也是 3 行的文本框被套用上次坐标」的隐患。

**分步 trace**：`fdSplitTrace()` 每步同步写 `recover/split-trace.log`（open/write/close），原生崩溃时最后一行就是崩溃点。这段日志也已附进诊断报告，用户贴一份文本即可。

## 真正的根因：iframe 里的 CEP 桥不回话（2026-11-10 10:15）

上一轮改成几何回传后，界面还是卡。加了超时之后终于拿到确定结论：**`fdPingLite()` 这种只读 `app.version` 的函数，15 秒都不返回**。函数本身毫秒级，所以不是慢，是调用根本没到 Host。

**架构问题**：面板 UI 跑在 iframe 里（页面由本地服务 `http://127.0.0.1:47615` 提供，好处是改界面不用重装扩展）。而 CEP 的 `window.__adobe_cep__` 只在**顶层扩展页**真正绑定到 Host —— 在跨源 iframe 里这个对象**存在**（所以 `typeof !== "undefined"` 判断为真）、调用**也不抛错**，但回调永远不回来。

这解释了两个现象：

- 最早 `fdRecoverScan` 点了没反应 —— 当时以为是 `doc.exportFile` 卡住，其实连 JSX 都没执行
- 现在 `fdPingLite` 15 秒超时 —— 同上

**修法**：加一层 postMessage 桥。

```
iframe (app.js)  --postMessage--> 顶层 (bridge.js)  --evalScript--> Illustrator
                 <--postMessage--                    <--回调-------
```

- `apps/cep/js/bridge.js`：顶层页执行 JSX，把结果发回 `e.source`
- 来源校验用 `e.source === frame.contentWindow` 而不是 `event.origin`
  —— CEP 的 CEF 在 file:// 顶层页面下 origin 可能是 `file://` 也可能是空串，按 origin 过滤会把自己的消息挡掉
- `app.js` 的 `evalJsx` 分两条路：`window.parent === window` 直调，否则转交父窗口
- 「应用到选中的文字」原来也是直接摸 `__adobe_cep__`，同样一直是坏的，一并改走 `evalJsx`

**教训：CEP 里只要 UI 在 iframe 里，`__adobe_cep__` 的存在不等于能用。** 判断"桥通不通"只能靠一次真实的 evalScript 往返，不能靠 `typeof`。

## 转曲恢复改为「几何回传」（2026-11-10 09:30）

**症状**：面板点「识别选中的转曲文字」后，永久停在「正在读取选区、导出图片…」，按钮一直是灰的，没有任何报错。

```
                   → 顺手算出每个轮廓的**精确像素包围盒**（聚类要的真值）
        ↓
原来的 聚类 → 逐字裁剪 → RapidOCR 流程完全复用
```

顺带解决的三件事：

1. **不动用户文档**。原来的方案增删画板，虽然可撤销，但会在面板操作里改用户的画板列表；现在完全不碰。
2. **位置更准**。包围盒由矢量直接算，不再靠导出图反推。
3. **不写临时 PNG 也就没有白底/透明度设置的问题**（`ExportOptionsPNG24` 根本没有 `matte`/`matteColor` 属性，之前那两行是指给 GIF/JPEG 用的）。

**同时给 `evalJsx` 加了超时**（探活 6s / 取几何 30s）。以后再有类似卡死，界面会直接说明「Illustrator 没有在 N 秒内响应」，而不是干等。另外把 `EvalScript error`（脚本没加载）单独识别成「请完全退出 Illustrator 后重开」。

**踩坑**：超时加上之后第一次就误报了 —— 探活用的 `fdPing()` 里读了 `app.textFonts.length`。这个属性会为每个已安装字体实例化对象，本机 1104 个 face，光枚举就要好几秒，于是 6 秒超时被吃掉，界面报「AI 没有响应」，把「慢」当成了「死」。改用 `fdPingLite()`：只读 `app.version` 和 `app.documents.length`，毫秒级；顺带回传 `hasGeom` 用来判断面板加载的是不是新版脚本（旧版直接提示重开 AI，不用猜）。**教训：CEP 的探活函数绝不能碰 `app.textFonts`。**

**验证**：`scripts/test-recover-geom.ts` 用 fontkit 把真实字体轮廓合成成与 AI 回传同格式的数据，走完整 HTTP 链路 —— **3/3 句完全正确**（SimHei「订单编号」、MicrosoftYaHei「设计改变生活」、SimSun「永和九年岁在癸丑」），渲染出的位图笔画完整、闭合字空洞正确。

## 转曲文字恢复（2026-11-09 19:10）

把已经转曲的文字变回可编辑文本。和字醒同功能，但实现路径不同。

**核心判断：不做整行 OCR。**

字醒的做法是「整块区域 OCR（带检测框）→ 按识别结果对齐位置」。实测这条路在转曲场景不成立：

| 引擎 | 结果 |
|---|---|
| tesseract.js（纯 npm） | 「永和九年岁在癸丑」→「水和九年岁在奖丑」，逐字 53% |
| RapidOCR 整行（默认检测） | 短句全对，长句被切成重叠块，拼出「永和九年**九年**岁在癸丑」 |

调 `unclip_ratio` 1.6→4.0 只会更糟（「订单**丁单编单编**号编号2号2024」）。PaddleOCR 的 DB 检测器面对「单行、无上下文、字距均匀」的图会过度分割。

**但转曲文字根本不需要检测** —— 每个字本来就是独立矢量轮廓，位置是精确真值。所以改成：

```
AI 读每个轮廓的包围盒 → 服务端按字宽聚成字 → 每个字单独裁剪识别 → 位置用真值
```

逐字识别（关掉 `use_text_det` 直接用 `text_recognizer`）：**9/9 案例全对，6ms/字**。

技术栈：Node 服务 + 常驻 Python 子进程（RapidOCR，PaddleOCR 的 ONNX 版）。模型加载 0.88s，之后每字 6ms。协议是 stdin/stdout 一行一个 JSON。

**聚类是最容易错的一环。** 转曲后一个字可能是 1 个复合路径，也可能散成好几个独立路径（「三」= 三条线）。踩过的坑：

1. 一开始用「间隙阈值」判同字 → 失败。中文紧排字间距只有 0.1em，比「川」「三」字内的笔画间隙（0.15em）还小，按原理分不开。
2. 改用「一个字宽作上限贪心合并」→ 成立。中文等宽，一个字宽 ≈ 字高，加上下一块会不会超一个字宽就能判。
3. 字高不能按单框估 → 一个字被拆成上下两半时只有半个字高。必须用**行高（该行竖直并集高度）**。
4. 分行要留容差（0.15 倍粗估字高）→ 否则上下相接的两半会被分成两行。

**图像增强**（Python 侧）：
- 深底白字反相 —— 判据不能用边缘像素（裁剪框就是墨迹框，四条边必然压在笔画上，会全判成深底导致整段识别为空）。改用 Otsu 双峰 + 暗像素占比 > 62%。
- 补到接近方形 —— 「一」「丨」宽高比太极端，识别器 resize 后几乎没信息。
- 识别为空时加大留白重试 —— 救回了「价格：128.00元」里的全角冒号。

**坐标换算**：图片 y 向下、AI 文档 y 向上。`x = originX + px/scale`，`y = originY + (pngH - py)/scale`。这块极易出错 —— 我在测试脚本里把基线偏移写成 `descent` 而不是 `ascent`，整排框偏上、只套住字的上半截，表现是识别结果大面积为空。

## 字体匹配（同 19:10）

反推原稿用的字体，接的是完整闭环。

## 字形相似度引擎（P0，2026-11-09 16:45）

从「字醒」那套 AIP 方案里借思路做的能力：给字体找「长得像」的邻居。

**算法演进（三次调整，每次都有实测数据支撑）**

| 版本 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 1 | 32×32 位图 IoU | 同款不同字重只有 0.574，异款反而 0.826 | 字重敏感度盖过设计差异，废弃 |
| 2 | 膨胀/腐蚀归一化笔画后 IoU | 32×32 上形态学操作破坏字形，分数更低 | 分辨率不够，废弃 |
| 3 | 64×64 位图 → 16×16 密度向量 → 余弦 | 同族/跨族间隔 +0.198 | **采用** |

余弦相似度对整体线性缩放天然不敏感（B = k·A 时 cos = 1），笔画粗细变化几乎不影响分数，而字形结构差异保留在密度分布里。

**性能坑**：`@resvg/resvg-js` 每次渲染 746ms（每次重建渲染上下文），781 字体 × 4 字要 39 分钟。改成自写扫描线填充（even-odd），单字形约 0.1ms，全量构建 28 秒。反正最后要二值化，不需要抗锯齿。

**重复检测换判据**：字形指纹会误报——微软那批 `LeelawadeeUI / NirmalaUI / SegoeUI` 共享拉丁字形，被判成同款。改用**文件 SHA-256**，「同一份数据」的严格定义，不会错。字形指纹降为辅助参考。

**能力边界（实测）**
- 能判断「是不是同类字体」：同族 vs 跨族间隔 +0.198
- 判断不了「同一款字体的不同字重」：间隔只有 0.014。Regular 和 Bold 的笔画粗细差一倍，结构差异比两款不同黑体还大，这是本质困难
- 「重复检测」用文件哈希解决，不靠相似度

**输出**
- `data/similarity.json` 960 KB：497 个字体的密度向量（base64）+ top-8 邻居 + 文件哈希
- `data/similarity-demo.html`：可视化验证页
- 实测推荐质量：宋体→新宋体 1.000 / 思源宋体 0.895 / 华文宋体 0.887；楷体→华文楷体 0.941；等线→等线粗体 0.944 / 华文细黑 0.913

**数据发现**：781 个 face 里只有 101 个含常用汉字（53 个家族）。`SimSun-ExtB`、`Malgun Gothic` 这类没有「永国人"的不参与，属于正确排除。参与相似度计算的 497 个中，CJK 99 / 西文 398。

## 家族归一化（B，2026-11-09 17:00）

原来的归键是 `familyZh || family` 小写，会把同一款拆成几户。改成「按 token 归一化英文家族名」。

**先量化再动手**：写了两个诊断脚本（`eval-family-key.ts` / `diag-family-split.ts`），对比四套规则的影响。结论是激进合并（去掉 sc/tc/hk/ui/vf 等地区与载体后缀）会把 `Wingdings 1/2/3`、`YaHei` 与 `YaHei UI`、`Nirmala UI` 与 `Nirmala Text` 这些**本来就该分开**的家族硬塞到一起——Illustrator 自己的字体菜单就是分开列的，合并了用户在面板里找到的家族在 AI 里又是另一个名字。

**采用的规则**（`packages/font-core/src/family.ts`）：

- 按分隔符 + 驼峰边界切 token：`NimbusSans` 与 `Nimbus Sans` 都得 `["Nimbus","Sans"]`，而 `Arimo` 保持单 token
- 只去末尾的款式词（Regular/Bold/Light/Medium/Book/Heavy/Thin…）
- 末尾纯数字：两位数直接去（`Avenir 65`），一位数只在已去掉款式词后才去（`Avenir 45 Book` 去掉，`Wingdings 2` 保留，否则 1/2/3 会被合并）
- 至少保留 1 个 token

**为什么不能按字符串末尾直接切**：第一版就是那么写的，结果 `Arimo` 因为末尾 `mo` 恰好是澳门地区代码被切成 `ari`。必须按 token。

**结果**：327 → 315 家族，**合并 10 组、拆分 0 组**（拆分 0 意味着不会把现有家族打散）。10 组逐条核过：`Avenir 45 Book`/`Avenir 65` 归回 Avenir（Adobe 的数字命名）、`Source Han Sans CN Bold` 归回本体（那个 face 的 subfamily 明明是「常规」，family 里却带着 Bold，是字体文件本身的数据损坏）、`思源宋体 CN` 与 `Source Han Serif CN` 跨语言合并。`Arimo`/`Wingdings`/`YaHei UI` 全部安全。

**撞名处理**：合并后 `Franklin Gothic Book/Heavy/Medium` 三个家族的 subfamily 都叫 `Regular`，列出来是三行一模一样的。加了 `variantLabels()`，撞名时把家族名里被去掉的款式词补回来（`Book Regular` / `Heavy Regular`）。

## 安装 / 卸载的设计约束

装字体是这套工具里唯一会动系统状态的操作，所以设了三道闸：

1. **只写用户级**：文件落到 `%LOCALAPPDATA%\Microsoft\Windows\Fonts`，注册表只写 HKCU。不碰 `C:\Windows\Fonts`，不需要管理员。
2. **只卸自己装的**：卸载前必须能在台账（`%LOCALAPPDATA%\FontDeck\installed.json`）里找到这条记录，并且文件路径必须位于用户字体目录内。系统字体一律只读。
3. **卸载不真删**：文件移到 `%LOCALAPPDATA%\FontDeck\backup\`，可还原。

另外两个防御：写入注册表中途失败会回滚（删掉已写的值 + 删掉复制过去的文件）；注册名已被别的字体占用时直接拒绝，避免把系统字体顶掉。

## 踩过的坑（都记在这，别再犯）

### CEP 相关
1. **`host.jsx` 里不能写 `#target illustrator`**。这是 ExtendScript Toolkit 的预处理指令，CEP 加载 ScriptPath 时会解析失败，**连带整个 `window.__adobe_cep__` 都不注入**——表现是面板能显示但点什么都没反应。
2. 未签名扩展需 `HKCU\SOFTWARE\Adobe\CSXS.11/12/13` 的 `PlayerDebugMode="1"`。
3. manifest 对齐可工作的第三方插件：`ExtensionBundleVersion="1.0"`（两段）、`RequiredRuntime CSXS 6.0`（最低版本）、`Host Version="17.0"`（单值，非区间）、补 `<ExtensionData>` 段。
4. CEP 扩展只在 AI 启动时扫描，改完必须重启 AI。
5. **CEP 12 仍支持 Node.js 集成**（内置 Node 17.7.1 / Node-WebKit 0.62.1）。manifest 里写 `--enable-nodejs`，`window.cep_node.require` 即可用；`--mixed-context` 是可选（只影响是否与页面共享上下文）。据此面板可以自己 `<spawn>` 出外部进程，**不需要用户手动开任何窗口**。
6. **不要用 VBS 做隐藏启动**：`wscript.exe` 属于 Windows LOLBin，被企业安全策略直接拦。用 CEP Node 的 `spawn(..., { windowsHide: true, detached: true })` + `unref()` 更干净，实测父进程退出后子进程存活。
7. **spawn 必须重定向 stdio 到日志文件**。`stdio: "ignore"` 时服务起不来完全无迹可查，`detached` 又看不到控制台。写到 `data\service.log`。
8. **不要把"备用启动"写成自动兜底**。静默通道失败时自动调 `cmd`/`bat` 会留下一个控制台窗口，而窗口就是服务本体、不会自己退，用户体感是"卡住了一个黑窗口"。备用方式必须由用户主动点击触发。
9. **`start /min` 不等于无窗口**。它只是把窗口最小化到任务栏，依然可见。
10. **`spawn(node.exe, {detached: true, windowsHide: true})` 在 Windows 上不可靠**。libuv 中 `DETACHED_PROCESS` 与 `CREATE_NO_WINDOW` 互斥，detached 生效后子进程仍可能被 Windows Terminal 接管并显示窗口。**要启动控制台程序且完全无窗口，必须经由 GUI 子系统程序（`pythonw.exe` 之类）再用 `CREATE_NO_WINDOW` 拉起。**
11. 验证"进程是否有窗口"的可靠办法：`Get-Process -Id X).MainWindowHandle`，为 `0` 即无窗口。比看截图可靠。

### 渲染相关
5. **字形坐标不能乘 scale**。`x` 必须在字体单位空间累加，缩放只在外层 `<g>` 做一次，否则字形全挤成一坨。
6. **必须用 `preferredFamily` 而不是 `familyName`**。后者带字重后缀（"Alibaba PuHuiTi R"），一个家族会被拆成几十个。
7. **长名字体会画到画布外**，需要 `autoFit` 按宽度反推字号。
8. **`OS/2.sFamilyClass` 不可靠**（Malgun Gothic 被填成 script）。字体名关键词优先，OS/2 和 PANOSE 兜底。
9. **`loading="lazy"` 在 CEP 的 iframe 里不触发**，卡片会一直空着。分页已控制请求量，直接去掉。
10. **`drawer` 用 `translateX(100%)` 藏到右边界外，会把文档宽度撑大**，把顶栏右侧的按钮推出视口。`html, body` 必须 `overflow-x: hidden`。

### 工具坑（不是产品问题，但浪费过时间）
11. **Edge 无头截图受系统 125% 缩放影响**。传 `--window-size=420` 时实际视口是 510 CSS px，截图按 420 裁，右边内容会被切掉，看起来像"元素没渲染"。验证布局要用 `--dump-dom` 量 `getBoundingClientRect()`，别只看截图。

### 数据相关
12. 注册表值有**完整路径**与**纯文件名**两种写法。
13. 路径**正反斜杠混用**：`C:/Users/6/.../Fonts\DejaVuSans.ttf`。
14. 大小写不统一。
15. `.fon` 是 16 位 NE 可执行文件里的位图字体，不可解析；`.CompositeFont` 是 WPF 的 XAML 配置，根本不是字体。
16. **文件哈希必须按 face 算，不能按文件算**。`.ttc` 一个文件装十几个 face（Avenir 那个装了 12 个），按文件哈希会把它们全判成「互相重复」——23 组虚报，真实只有 5 组。key 要带上集合索引。
17. **字体家族名里会带着字重后缀**，而且和 subfamily 矛盾：`Source Han Sans CN Bold` 这个 face 的 subfamily 明明是「常规」。这是字体文件本身的数据损坏，不是解析错。
18. **同款字体可能同时装在系统目录和用户目录**（Raleway、Malgun Gothic 都是），不是索引重复，是真占了两份磁盘。

|---|---|
| `GET /api/health` | 探活 |
| `GET /api/stats` | 统计 |
| `GET /api/families` | 家族列表（分页、筛选、搜索） |
| `GET /api/fonts` | face 列表 |
| `GET /api/fonts/:id` | 单个 face 详情 + 同家族字重 |
| `GET /api/fonts/:id/preview.svg` | SVG 轮廓预览 |
| `GET /api/installed` | 安装台账 |
| `POST /api/install` | 按本地路径安装（CEP 文件对话框） |
| `POST /api/install-raw` | 直接上传二进制安装（浏览器拖拽） |
| `POST /api/uninstall` | 卸载（移入备份） |
| `POST /api/restore` | 从备份还原 |
| `POST /api/recover/geometry` | 转曲恢复主入口：收 AI 回传的原始路径几何 → 服务端渲染 → 分行 → 整行 OCR（自动语种切换） |
| `POST /api/recover/recognize` | 转曲恢复：聚类 + 逐字识别，入参是 AI 侧 fdRecoverScan 的返回 |
| `POST /api/recover/match` | 转曲恢复：反推原稿字体，返回归一化后的候选列表 |
| `POST /api/feedback/report` | 一键诊断日志，落盘 `data/feedback/FD-*.json` + `.txt` |
| `POST /api/usage/hit` | 常用字体打点（打开详情 1 / 恢复里被采用 2 / 应用到选区 3） |
| `GET /api/usage/top` | 常用字体家族榜，`items[].psList` 是该家族全部 ps 名（整族删除用） |
| `POST /api/usage/remove` | 从常用里整族移除，返回被删的 `{key:{n,t}}` 供撤销 |
| `POST /api/usage/restore` | 撤销移除，原样写回计数 |

筛选参数：`q` / `cat` / `lang` / `scope` / `health` / `dup` / `offset` / `limit`

`dup` 有两个取值：`1` 同名重复（PostScript 名撞车）、`hash` 文件内容逐字节相同。

`GET /api/fonts/:id` 除字体本身外还返回：
- `siblings`：同家族字重，每条带 `label`（撞名时已加前缀区分）
- `similar`：6 个不同家族里字形最像的，含 `score`
- `fileDupes`：磁盘上内容相同的其它副本，含 `filePath`

常用区（`data/usage.json`）**只收录"真的应用过"的字体**（记录里的 `a > 0`）：
应用到选区 +3、转曲恢复里采用 +2、只打开详情 +1（只记总分 `n`，不计入常用）——
光翻列表不该把常用塞满。前 3 个常显，其余收进托盘。
右键任一卡片进入多选 → 「移除」→ 8 秒内可「撤销」。
**必须整族删**（用 `psList` 一次提交）：只删用得最多的那个 face，同族别的字重还留着计数，卡片下一轮就会重新冒出来。

卡片是**单行列表 + 悬停预览**：一行一个字体，上排「字体名（SVG）+ 字重/分类/字重数/格式」，
下排「样张 + 徽标」；鼠标停 100ms 原地向下长到 126px，露出放大字样和 PostScript/格式/体积。
展开不闪的两个前提：卡片绝对定位在固定 58px 的 `.slot` 里（只改自身高度，相邻行不重排）；
高度**必须走 px 过渡**（CSS 的 `100%` 与 px 不插值，混用会瞬间跳变，所以先写起点 px +
`void offsetHeight` 强制回流，再写终点）。视口底部放不下时改为向上长。

写操作会校验 `Host` 头必须是 `127.0.0.1` 或 `localhost`，防止外部网页通过 CSRF 往本机装字体。

## 恢复后的垂直对位（2026-11-18）

用户反馈「有一点点向上位移，不同字体位移不一样」，两个原因叠在一起：

1. `textFrame.visibleBounds` 的下边未必是字形墨迹底。若是行框底（= 基线 − descent×字号），
   直接拿它对位会让整行按 descender 上移。现在服务端按每个候选字体实测两项
   （`/api/recover/match` 返回 `descent` / `inkBottom`，由 worker 的 `metrics` 命令
   用 fontTools 读表 + PIL 渲染实测），前端合成 `lift = descent + inkBottom` 随 item
   传到 AI 侧，定位时先把行框底抬回墨迹位置。
2. AI 改完 `size` 之后 `visibleBounds` 偶尔还滞后一帧 —— 第一刀总会差一点点，
   差值随字形变化（这正是「换字体偏移量就变」的来源）。现在移动完**再读一次边界**，
   把残差补掉（只补位置、不动字形，残差 < 0.02pt 就停）。

apply-trace 里新增 `lift / dy / resid / fixed / boxH/size`：
`boxH/size` ≈ 0.9 说明 visibleBounds 是墨迹框，≈ 1.0~1.35 说明是行框 ——
下次再报位置问题，看这一个数就能分辨是「语义不对」还是「读值滞后」。

## 下一步

- 字体匹配的已知短板：分不开同款的不同字重（Similarity 那条实测间隔只有 0.014）；雅黑与普惠体这类极像的同族会被排在一起

- 分类准确度：「未分类」占比偏高，中文字体需要更好的启发式
- 安装界面可以再加：拖入前的字体信息预览、批量安装进度
- 索引缓存：现在每次启动都全量扫（1.5s），可落盘缓存到 `data/index.json` 做增量刷新
- 相似度的已知短板：中文字体里「无衬线」和「衬线」的分数区间有重叠（宋体的推荐里会混进 MiSans 86%）。要分清得加「衬线特征」维度，不是调参能解决的
